insarwatch-code

Technical reference for seven dependency-free Python calculators used in geotechnical engineering, surveying and InSAR monitoring.

Source on GitHub Online calculators (Spanish) Cite this repo

What this repository is

Field geotechnical work still runs on spreadsheets: one tab per soil layer, Boussinesq formulas pasted from a textbook, unit conversions hidden inside a cell, and nested IF() chains that nobody can audit six months later. Two engineers given the same borehole log routinely produce different numbers, and neither can show exactly how the result was obtained.

This repository is the opposite of that. It contains seven small Python modules, each one a pure calculation with no state, no I/O beyond its own worked example, and no third-party dependencies. You can copy a single file into your own script, read every line in a few minutes, and reproduce every digit by hand. The modules are the same algorithms that drive the free online calculators at insarwatch.com, whose interface is in Spanish because the intended users are engineers in Latin America and Spain.

The split is deliberate: the website is for a quick answer while you are on site; this repository is for when the calculation has to go into a report, a script, a peer review or a reproducible study. This English technical reference documents the equations, the input contracts, the worked examples and — just as importantly — the boundaries of what each module does not do.

Design decisions

Standard library only

Every module imports math and nothing else. There is no numpy, no scipy, no plotting stack and no package install step. That is a practical constraint, not a stylistic one: a script that must run on a site laptop, inside a CI job, or on a university server five years from now should not depend on a resolver. It also means the regression fits and the iterative solvers are visible in plain code rather than hidden behind a library call.

The error contract

Functions return a dictionary on success and a dictionary with an error key on invalid input, or None when the geometry is impossible. They never raise for ordinary bad data, never print to the console in library mode, and never contain user-facing text. Error values are language-neutral codes such as invalid_input, insufficient_points or ip_negative. That contract exists because the same calculations are exposed through a Spanish web UI: the browser layer decides what a person should read, while the calculation layer stays free of wording that would need translating.

Units are fixed, not inferred

Nothing guesses units. Unit weights are kN/m³, stresses kPa, water content and saturation are percentages, level differences are millimetres, distances are metres, angles are degrees, and the unit weight of water is a fixed 9.81 kN/m³. Feeding feet, psi or radians will produce a numerically valid but physically wrong answer. Convert before you call.

Auditability over convenience

Each module ends with an if __name__ == "__main__" block that prints a hand-worked example with numbers you can check with a calculator. The intermediate quantities — regressions residuals, slice geometry, per-station deflections — are returned in the result dictionary rather than discarded, so a reviewer can reconstruct the whole path from input to answer.

Quick start

git clone https://github.com/yusheng-zhang-star/insarwatch-code.git
cd insarwatch-code
python python/fases_suelo.py        # prints the worked example
python python/slope_core.py         # prints the three factors of safety

Or import a single function into your own code:

from fases_suelo import from_gsw

r = from_gsw(2.70, 18.0, 15.0)   # Gs, gamma (kN/m3), w (%)
print(r["e"], r["S"], r["gsat"])  # 0.6923  0.5850  19.67

There is no packaging step and no entry point to configure. Add the python/ directory to your path, or copy the file you need.

Module reference

1. fases_suelo.py — soil phase relations

Turns the three quantities a laboratory actually reports into the ones a design needs: void ratio, porosity, degree of saturation, and dry, saturated and submerged unit weights.

Inputs

from_gsw(Gs, gamma, w) with w in percent, or from_ges(Gs, e, S) with S in percent. Any three independent values determine the rest; these are the two triples used in practice.

Equations

gamma  = Gs * gw * (1 + w) / (1 + e)      gw = 9.81 kN/m3
n      = e / (1 + e)
S * e  = w * Gs
gamma_d    = gamma / (1 + w)
gamma_sat  = (Gs + e) * gw / (1 + e)
gamma'     = gamma_sat - gw

Worked example

Gs = 2.70, gamma = 18 kN/m³, w = 15 % gives e = 0.6923, n = 0.4090, S = 0.5850, gamma_d = 15.65, gamma_sat = 19.67 and gamma' = 9.86 kN/m³.

Boundaries. A non-positive void ratio returns None because the inputs are physically inconsistent. Saturation above 1 is allowed through rather than silently clamped — it is a useful signal that a lab value is wrong. The module performs no unit conversion, no temperature correction to gw, and no organic-soil or unsaturated adjustment.

2. shear_strength.py — Mohr-Coulomb envelope

Fits cohesion c and friction angle phi to direct shear or triaxial test data by least squares, and returns R², per-point residuals and 95 % confidence intervals.

Equations

Direct shear:  tau = c + sigma_n * tan(phi)      (direct regression)
Triaxial:      p = (sigma1 + sigma3) / 2
               q = (sigma1 - sigma3) / 2
               q = c * cos(phi) + p * sin(phi)

Fitting in p–q space is the important detail: a triaxial specimen gives a Mohr circle, not a point on the envelope, so treating sigma1 as shear stress and sigma3 as normal stress is a classic error this module avoids.

Statistics

The regression is computed in centred form. Confidence limits use the 0.975 quantile of Student's t for 1–30 degrees of freedom from a hard-coded table, and 1.96 beyond 30. Nothing is sampled and nothing is estimated numerically.

Worked example

Direct shear points (100, 55), (200, 90), (300, 130), (400, 175) in kPa give approximately c = 15 kPa and phi = 21.8° (tan(phi) = 0.40). A companion triaxial set is printed by the same example block.

Boundaries. At least two points are required; identical x-values return None. Triaxial specimens with sigma1 < sigma3 are dropped, and a fitted sin(phi) outside (-1, 1) returns None. The intervals assume independent, roughly normal residuals — a reasonable classroom assumption, not a substitute for engineering judgement on three scattered specimens. Pore pressure and effective-stress corrections are not applied; feed effective stresses if that is what your envelope needs.

3. atterberg.py — Atterberg limits from the flow curve

Fits w = a·log10(x) + b by least squares and reads the liquid limit off the fitted curve, then derives the plasticity and liquidity indices and the position on the Casagrande chart.

Equations and conventions

Casagrande cup:  x = blow count N,      LL = w(N = 25)
Fall cone 76 g:  x = penetration d (mm), LL = w(d = 20)
IP = LL - LP                 IL = (w_n - LP) / IP
A-line: IP = 0.73 * (LL - 20)   U-line: IP = 0.9 * (LL - 8)

Worked example

Three points generated from w = -10·log10(N) + b with LL = 40 % recover LL = 40.0 %, R² = 1.0000; with LP = 18 and w_n = 28 the module returns IP = 22.0 and IL = 0.455.

Boundaries. Rows with non-positive x or w are discarded, fewer than two valid rows yields insufficient_points, a negative plasticity index yields ip_negative, and IL is None when IP is effectively zero or no natural water content was supplied. The module reports whether the point lies above the A-line and whether it exceeds the U-line; it does not output a USCS symbol, and it does not extrapolate beyond the measured range of the flow curve.

4. slope_core.py — critical circular slip surface

The largest module. It discretises a homogeneous slope into 24 vertical slices and searches a grid of circle centres and radii for the minimum factor of safety using three methods on the same geometry: Fellenius (ordinary), simplified Bishop and Spencer (1967).

What the solver actually does

Fellenius sums resisting and driving forces directly, keeping the signed slice-base angle. Bishop iterates a fixed point on m_alpha = cos(alpha) + tan(phi)·sin(alpha)/FS for up to 200 iterations and rejects circles where m_alpha becomes non-positive. Spencer performs a nested bisection: for each interslice force angle theta in ±60° it solves horizontal force equilibrium for FS, then bisects theta until moment equilibrium is satisfied. To keep the cost sane, Spencer is only evaluated on the 30 best Bishop circles, and a physical gate rejects a Spencer result more than 1.3 times the Bishop value of the same circle.

An optional pseudo-static seismic coefficient kh enters all three methods: Fellenius reduces the normal force by kh·W·sin(alpha) and adds kh·W·cos(alpha) to the driving force; Bishop adds the horizontal term to the driving force only; Spencer adds kh·W to horizontal equilibrium and its moment to the moment sum. Default kh = 0 is static.

Worked example

search(H=8, beta=25°, gamma=18, c=50, phi=35°, step=2) is a deliberately stable slope; the module prints how many circles were tried and the minimum FS from each method.

Boundaries — read this before using it in a report. Pore-water pressure is taken as zero, the slope is a single homogeneous dry material, there are no tension cracks, no surcharge, no reinforcement, no layers and no 3D effects. The answer is only as good as the grid step: a coarse step can miss the critical circle. Spencer may return None when no sign change can be bracketed, which is reported rather than replaced with a plausible-looking number. This is a screening and teaching kernel, not a limit-equilibrium design package and not a substitute for a geotechnical model.

5. alerta_umbral.py — InSAR velocity screening

Classifies a deformation velocity (mm/yr) and an optional acceleration (mm/yr²) into green / yellow / red.

classify(velocity, acceleration=None, yellow=10, red=50)
level = red if |v| >= red else (yellow if |v| >= yellow else green)
acceleration trend: > 0.05 accelerating, < -0.05 decelerating
accelerating: yellow -> red, and green at |v| >= 0.7*yellow -> yellow

The acceleration rule reflects a real precursor pattern: a modest velocity that is picking up speed is often more concerning than the same velocity held steady. Worked example: 5 → green, 28 → yellow, 80 → red, (30, +10) → red, (8, +3) → yellow.

Boundaries. The defaults of ±10 and >50 mm/yr come from the InSAR slope-monitoring literature (Wasowski & Bovenga 2014 and several SBAS case studies; the upper value is associated with field-observed cracking and damage to roads). They are screening values, not a code, standard or regulation. There is no universal normative threshold — the governing values must come from the project's monitoring plan and the applicable local standard. The module does no time-series analysis, no atmospheric correction, no coherence or spatial clustering, and no line-of-sight to vertical conversion. It is a classifier, not an early-warning system.

6. nivelacion.py — level-loop closure

Computes the misclosure of a geometric levelling run, checks it against a tolerance, distributes the correction and reports relative precision.

fh      = sum(dh) - dh_known          (closed loop: dh_known = 0)
E       = k * sqrt(L)                 L in km, k in mm/sqrt(km), default 20
v_i     = -fh * d_i / sum(d)          proportional to distance
1:T     = |fh| / sum(d)
passes  = |fh| <= E

Worked example

Three legs of +1000, -600, -395 mm over 200, 150, 250 m give fh = 5 mm, E = 20·sqrt(0.6) = 15.49 mm and 1:120, so the loop passes. The per-leg corrections are returned in corrected for the field book.

Boundaries. Distribution is by distance only, not by number of instrument setups. The default k = 20 corresponds to ordinary / fourth-order work; choose the value your specification requires. This is a single-run closure check, not a least-squares network adjustment, and it does not propagate variances, refraction or curvature corrections.

7. curva_circular.py — simple circular curve

Given a deflection angle and a radius, returns the six curve elements and a stakeout table by deflections.

T = R*tan(D/2)          E = R*(sec(D/2) - 1)
L = R*D (D in radians)  C = 2R*sin(D/2)
M = R*(1 - cos(D/2))    degree = 1145.9156 / R  (deg per 20 m chord)
delta = l / (2R)        chord = 2R*sin(delta)

Worked example

D = 60°, R = 100 m gives T = 57.74 m, E = 15.47 m, L = 104.72 m, C = 100.00 m, M = 13.40 m and D = 11.46°/20 m. The stakeout loop emits full 20 m stations and then the final fractional station at L, so the endpoint is never dropped.

Boundaries. Requires 0 < D < 180° and R > 0. Simple circular curves only: no transition spirals, no superelevation, no compound or reverse curves, and no conversion into coordinates or azimuths. Output is a table of arc distances, deflection angles and chords, not a setting-out file for a total station.

How the numbers are verified

There is no black box. Every module ships a worked example in its __main__ block whose intermediate values are written out in the comments, so you can check the arithmetic independently. Running the file prints the result; reading it shows the derivation.

The website calculators are implemented in JavaScript and the repository modules in Python. They are kept deliberately independent: the same formulas are written twice, in two languages, and their outputs are compared. The slope-stability core is verified bit-identical against the JavaScript that runs on the live site — the same circle grid, the same slice geometry and the same Fellenius, Bishop and Spencer implementations. Across all seven modules the published agreement target is better than 0.1 %.

The consolidated hand calculations live in examples/verification.md. If you change a formula, change both implementations and update that file; a pull request that only changes one side will be asked to reconcile them.

If a result looks wrong, check the units first. Almost every disagreement between this code and a spreadsheet is a percent-versus-ratio or degree-versus-radian conversion, not a formula error.

Why the InSAR thresholds are labelled as screening values

Searching for a single normative velocity limit for InSAR slope monitoring does not produce one: published values are study-specific and depend on the sensor, the time window, the geometry and what is being protected. The module therefore ships literature-derived defaults — roughly ±10 mm/yr as a stable/unstable boundary and above 50 mm/yr as a level associated with observed damage — and says plainly on the tool page that they are not a standard.

This is an unusual thing to put in a README, but it matters for anyone citing the code. A calculator that quietly presents a literature value as a legal limit is worse than no calculator. The thresholds are parameters you are expected to replace with the ones in your monitoring plan, which is why yellow and red are arguments rather than constants you have to edit.

Frequently asked questions

Do I need numpy, scipy or a virtual environment to run these modules?
No. Every module imports only the Python standard library math module and runs on Python 3.8 or newer. Clone the repository or copy one file into your project and run it directly.
Can I use the results in a commercial geotechnical report?
Yes. The repository is MIT licensed, so you may use, modify and redistribute the code. You are responsible for the engineering judgement and for checking the calculations against your project requirements; the license covers the code, not the design.
Why do functions return error codes instead of raising exceptions or showing messages?
The same calculations back a Spanish-language website. Keeping the computation layer free of exceptions and of user-facing wording lets the interface choose the message, and keeps the modules usable in batch scripts where one bad row should not stop a whole run.
How close are the Python results to the online calculators?
The agreement target is better than 0.1 percent for all seven modules. The slope-stability core is verified bit-identical against the JavaScript running on the live site, including the circle search and all three methods of slices.
Are the InSAR velocity limits a norm or a standard I can cite as a requirement?
No. They are screening values drawn from published InSAR slope-monitoring studies, not a code or regulation. There is no universal normative threshold. Set yellow and red from your project monitoring plan and the applicable local standard before using them for decisions.
Does the slope module handle pore pressure, layered soil or seismic loading?
Pore-water pressure is assumed zero and the slope is a single homogeneous material, with no layers, surcharge, tension cracks or reinforcement. A pseudo-static seismic coefficient kh is supported as an optional argument; everything else is outside the model.
Which units does the code expect?
Unit weights in kN per cubic metre, stresses in kPa, water content and saturation in percent, level differences in millimetres, distances in metres, angles in degrees, and a fixed water unit weight of 9.81 kN per cubic metre. The code does not convert units for you.
How should I cite this repository in a paper or thesis?
Use the CITATION.cff file at the repository root, which generates a standard software citation. At minimum, include the repository URL, the version or commit you used, and the module name, so a reader can reproduce the exact arithmetic.

Citing and contributing

If you publish results obtained with these modules, cite the repository using CITATION.cff and state which version you ran. New calculators are welcome: prefer stdlib-only Python, keep the language-neutral error-code contract, add a hand-worked example and link the matching online tool. The issue templates in the repository cover both a calculation proposal and a discrepancy report.
